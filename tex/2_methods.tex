\chapter{Methods} 
In this section we discuss the methods applied to find similar reviews in the \textit{Yelp} dataset.

To study the similarity between documents we have extracted tokens from each review. In Section~\ref{methods_preProcessing} we outline how we have codified the original strings by extracting the most relevant information.

\section{Data pre-processing}\label{methods_preProcessing}
We would like to subdivide the reviews into smaller items on which to base our similarity evaluation. Usually one proceeds by considering the $k$-grams of a textual document, but since we want to focus on the semantics of the text, we prefer to take as tokens simply the words composing a review. We also concentrate our study on the meaning of the sentences by removing all stop words. We considered as English stopwords those provided by the \texttt{nltk.corpus} package. For the same reason we lemmatized all tokens by using the method provided in the \texttt{spacy} module. Also, for each review we maintain each token once. In this way we codify each review through it's essential information. In Section~\ref{similarItems} we explain how we can determine the affinity between reviews by comparing the elements that compose their summary.

\section{Similar items with Jaccard similarity}\label{similarItems}
In this section we analyze the similarity between the reviews using Jaccard similarity (Section~\ref{JaccardSimilarity}) between sets. To compute the affinity between pairs of reviews in Section~\ref{reviewSummaries} we introduce a succint way of storing the tokens contained in each summary of the review. This data structure we will show to be linked to the Jaccard similarity, so it is ideal for our scope. It will become evident that manipulating this data structure for our analysis is not at all efficient, so in Section~\ref{LSH} we will look at an approximate solution for determining similar items.

\subsection{Jaccard similarity}\label{JaccardSimilarity}
The Jaccard similarity between sets $S$ and $T$ is defined as:
\begin{equation}
    J(S,T)=\frac{|S\cap T|}{|S\cup T|}
\end{equation}
Simply put, we look at the elements that appear in both the sets.
In our case the items of the sets are the tokens that we have extracted from the reviews. So we are interested in looking at the number of tokens that are shared among a pair of reviews.

\subsection{Similarity preserving summary of the reviews}\label{reviewSummaries}
To compute the Jaccard similarity we prefer to keep the extracted information about the reviews in a so called \textit{characteristic matrix}, used to represent a collection of sets. In particular we have a matrix $M\in \{0,1\}^{t\times r}$ where $t$ is the cardinality of the universal set of tokens, and $r$ is the number of reviews. The cell $M_{ij}$ is $1$ if token $i$ is present in the summarized version of review $j$.\newline

With growing amounts of data it is not possible to store the whole characteristic matrix, neither by considering the non-null cells. In fact the dimensions of the matrix are bound by the quantity of rows, which in our case are the number of tokens extracted from all reviews. As a consequence one is obliged to store the information given by the reviews in a compact way. We have decided to adopt a data structure that has some interesting property with respect to the Jaccard similarity, namely a \textit{signature matrix}. Each row of such matrix is constructed as follows:
\begin{enumerate}
    \item choose a permutation of the rows of the characteristic matrix uniformly at random among all possible permutations,
    \item apply the chosen permutation to the rows of the characteristic matrix,
    \item apply a minhash function to all columns of the resulting matrix.
\end{enumerate}
A minhash function is defined as $h:\{ \text{sets} \}\to \{ \text{item\_indexes}\}$, and for a given set it returns the index of the first 1 in the indicator vector of the items for the document. The pseudo-code for constructing a signature matrix from the characteristic matrix is given in Algorithm~\ref{alg: signatureMatrix}.

\begin{algorithm}
    \label{alg: signatureMatrix}
    \caption{Construct a signature matrix from the characteristic matrix of a collection of sets}
    \begin{algorithmic}[1]
        \Input
            \Statex $r \in \{1,\dots,R\}$ item
            \Statex $c \in \{1,\dots,C\}$ set
            \Statex $h_i \in \{h_1,\dots,h_I\}$ hash function
        \EndInput
        \Statex
        \State Initialize all entries of matrix SIG$\in \mathbb{N}^{I,C}$ to $\infty$
        \For{$r = 1,\dots,R$}
            \For{$i = 1,\dots,I$}
            \State compute $h_i(r)$
            \EndFor
        \EndFor
        \For{$c \in 1,\dots,C$}
            \If{$\text{CHAR}(r,c)=1$}
                \For{$i = 1,\dots,I$} 
                    \State $\text{SIG}(i,c)=\min\{\text{SIG}(i,c),h_i(r)\}$
                \EndFor
            \EndIf
        \EndFor
        \Statex
        \Output { SIG}
        \EndOutput
    \end{algorithmic}
\end{algorithm}

\subsection{Locality-sensitive hashing (LSH)}\label{LSH}
It would be unthinkable to compare all possible pairs of reviews to find similar ones among them. This would also mean scanning all the rows in the signature matrix to compute the relative frequency between possible pairs of reviews. So, we proceed by applying Locality-Sensitive Hashing. In this approach we filter on pairs of reviews by hashing them several times and only looking at those couples collected in the same bucket. The rationale is that similar reviews are more likely to be hashed in the same bucket, so we hope that dissimilar pairs end up in distinct buckets, and thus are never checked for similarity.
